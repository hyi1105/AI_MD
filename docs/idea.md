# Idea（進行中的構想）

> 用途：你分享想法 → AI 整理對話 → **寫入本檔**。  
> 與 [`idea.history.md`](./idea.history.md) 分開：查構想時先讀本檔即可，**少載入舊資料、省成本**。  
> [`03-checklist.md`](./03-checklist.md) 是「現有功能查核表」，不是構想匣。  
> 做成並發布後：把該能力**登記進 checklist**；本則構想再移到 `idea.history`。  
> 合作規則總表：[`../prompts/AGENT-MASTER.md`](../prompts/AGENT-MASTER.md)  
> 更新：2026-08-13

### 寫入規則（給 AI）

負責人每說一則構想（含語音轉文字），AI 必須：

1. 改寫成**繁體中文**  
2. 用下方完整模板補齊（缺的標「待補／待拍板」）  
3. **追加**到本檔最上方  
4. 未真正具備的功能不要塞進 checklist；checklist 只登記「現在應該查核得到」的能力  

### 完整模板（每則必用）

```markdown
## YYYY-MM-DD — 短標題
- 狀態：open｜building｜waiting-owner
- 來源：對話／語音轉文字（可註原文關鍵句）
- 為什麼（Why）：要解決什麼問題？不做會怎樣？
- 做什麼（What）：使用者會看到／能完成的具體結果（1～3 句）
- 怎麼做（How）：實作方向、改哪些檔／流程、依賴什麼
- 優點（Pros）：做成後的好處
- 缺點／風險（Cons）：成本、複雜度、安全、維護、對現有功能影響
- 不做的替代方案：若不做，有沒有較小做法？
- 完成後列入 checklist：查核句（給 checklist 用，描述「產品應具備的功能」）
- 待拍板：需要負責人決定的問題（無則寫「無」）
```

## 2026-08-13 — 系統地圖再強化：拼圖式圖像化

- 狀態：open  
- 來源：對話（原文：「有越來越合胃口」「我喜歡的拼圖」「圖像化」）— 對已上線 `/system-map/` 的口味回饋，指向下一版視覺語言  
- 為什麼（Why）：現況四視角已「同地圖換鏡頭」，但右側仍偏文字卡／程式碼塊，拼圖感不足。負責人明確喜歡**拼圖＋圖像化**；若不沿這條加強，容易停在「說明文件切換」而不是「可拼的圖像地圖」。  
- 做什麼（What）：系統地圖看起來像在拼一塊系統：每個節點是一塊有形狀／色邊的拼圖（或圖塊），層級＝可嵌套的拼板；切換 SQL／流程圖／PA／Shared Enclosure 時，**同一塊拼圖換皮**（圖示與紋理變、缺口對齊關係不變），一眼仍認得是同一節點。  
- 怎麼做（How）：  
  - 改 `web/system-map/`（需「改程式」才動）：節點改為視覺圖塊（形狀＋簡圖／圖示），少長文、多圖與短標。  
  - 拼圖語言：主幹兩塊（流程控／資料存）為大板；子節點為可拼上的小塊；焦點＝高亮缺角對齊。  
  - 四視角＝四套「皮」：流程圖＝箭頭軌道圖塊、SQL＝表／欄位圖塊、PA＝觸發－動作積木、Enclosure＝空間席位圖塊。  
  - 動效：切換視角時圖塊翻面或換皮（2～3 個有意動畫），不整頁重刷感。  
  - 先不擴新系統；繼續用簽核示範驗證口味。  
- 優點（Pros）：對齊負責人胃口；學習更靠空間記憶；與「統一場景」更像同一套玩具換皮膚。  
- 缺點／風險（Cons）：圖像資產與 CSS 造型成本；過度裝飾可能蓋過層級資訊；行動裝置拼圖密度要控。  
- 不做的替代方案：只加圖示到現有文字卡（小改）；或靜態一張總拼圖 PNG（不能互動切視角）。  
- 完成後列入 checklist：系統地圖節點以拼圖／圖塊呈現，且切換至少兩視角時同一節點圖塊可辨識為同一塊。  
- 待拍板：  
  1. 拼圖風格偏「真拼圖缺角」還是「積木／磁貼圖塊」（建議先積木／磁貼，較好做 RWD）？  
  2. 要不要現在就「改程式」做一版視覺加強？
